# 取证与缺口续查

围绕用户目标选择当前能推进结论的一步，沿用同一数据目录与任务记录。已有链接用 `read`／`read-many`；需要跨轮追踪多个对象或主张时，再使用 `research` 与状态文件。

## 目标与研究状态

区分用户明确要求、推断与待确认条件。为每个关键问题标明对象、时间、版本或其他影响结论的条件；比较多个对象时将对象写进字段名，例如“甲：支持范围”“乙：支持范围”。只有会影响判断的信息才需要单独跟踪。

CLI 从首轮指定状态文件，取得一批材料后核验：

```bash
sera research "某软件的版本与支持范围" --read-sources web --goal "版本与生效时间" --goal "功能及适用条件" --state ./research-state.json --read-limit 3 --json
```

文件不存在时按 `--goal` 建立；已存在时读取并原子写回。重复执行保留 Agent 核验过的字段、状态与证据 ID。MCP 首轮对应：

```json
{
  "query": "某软件的版本与支持范围",
  "readSources": ["web"],
  "goals": ["版本与生效时间", "功能及适用条件"],
  "readLimit": 3
}
```

`sources` 控制本次搜索与读取范围；搜索源不读取正文时用 `readSources` 另选。用户指定的来源、费用和访问限制在后续换路时继续生效；Agent 自选的单次来源列表可以根据取得结果调整。

从 `documents` 审阅片段，必要时续读全文，再更新 `state.fields`：

| 状态 | 含义与记录 |
|---|---|
| `pending` | 仍缺少足够材料，或尚未完成核验；在 `note` 写明缺口 |
| `supported` | 该字段已有证据支持的明确结论，在 `note` 写实际结论与适用条件；结论也可以否定原先待查说法 |
| `conflict` | 对齐对象和条件后仍有实质冲突，关联相关证据并说明争议 |

`candidates` 是待审阅材料与字段的关联，需由 Agent 核实支持关系。`evidenceIds` 只填实际返回的 SERA ID；宿主工具取得的材料在 `note` 或任务记录中保留原始 URL、观察时间、相关片段与记录路径，交付时按原始来源引用。

CLI 编辑状态文件的 `fields` 后重跑原命令；MCP 下一次调用 `sera_research` 时传回更新后的 `state`。保留 `examinedUrls`、候选与失败记录。`nextQuery` 建议聚焦一个未决字段、优先冲突；结合已有材料选择实际下一步。`nextAction` 的完成状态来自调用方确认的字段，交付前仍对照用户目标检查覆盖情况。

## 按缺口选取证方式

| 缺口原因 | 可用行动与应核对的内容 |
|---|---|
| 尚未找到相关材料 | 按实体、别名、语言、主张与原始发布者检索；结果无关时调整查询或来源 |
| 已有材料但当前片段不足 | 用 `query`／`keywords` 定位，按返回坐标续读所需上下文 |
| 需要精确字段或完整记录 | 读取适合该对象的 API、表格、附件或原始记录，核对字段含义和覆盖范围 |
| 需要交互、动态内容或当前状态 | 直接使用可用浏览器工具观察有关状态，读取交互后实际出现的内容 |
| 需要过去某时点的事实 | 核对目标时间与历史 URL，读取实际快照或对应修订 |
| 结论依赖图像、音视频或讨论 | 使用相应图像、字幕、原帖与评论入口，保留内容类型与读取范围 |
| 来源之间出现差异 | 先对齐对象、时间、版本和其他条件，再追溯原始记录或寻找能区分解释的证据 |

根据所需观察与可用能力选择入口。SERA 内相关入口不可用或不足时，可以在用户允许范围内用宿主搜索、浏览器或其他工具接力，并保留实际取得方法；成功材料可继续供下一轮使用。

浏览器观察记录与结论相关的页面状态，例如实际展开的内容、筛选条件、选中项、分页范围或生效版本；确认操作后目标内容已出现，再保留原文片段。需要布局、图表或图像解释时附截图。加载失败时记录失败入口与仍缺的信息，继续评估其他可用路径。

外部工具得到的 URL 可交回 `read` 取证；交互观察与再次读取的文本分别记录其方法、时间与条件。SERA 的网页抽取、上游可能缓存的渲染内容和宿主浏览器当前状态，按各自实际取得范围使用。

## 阅读与证据核验

```bash
sera read-many "https://example.org/spec" "https://example.org/changelog" --query "功能的适用条件" --keyword version --json
sera evidence EVIDENCE_ID --keyword requirements --length 1000 --json
```

替换为真实链接和已返回的证据 ID。`read-many` 最多20项、三路并行。默认读取预算为2000字符；`selection:focused` 的 `fragments` 保留原文坐标，`leading` 表示返回开头。用 `evidence` 的 `offset`／`length` 续读相关部分，全文在证据 ID 下保留。

逐层检查取得结果：

1. **请求响应**：查看实际来源、`runs` 与失败原因；有响应后继续判断相关性与内容。
2. **目标材料**：检查 URL／对象、正文、类型、完整范围及 `metadata`；识别错误页、验证页、摘要、元数据和正文各自能证明什么。
3. **结论支持**：确认原文是否直接支持待查主张，是否还缺上下文、条件、版本或独立证据。证据 ID 与 `ok` 表示工具记录，应结合原文审阅。

规则、声明与规范优先追到原始发布者；实际表现查观测记录，用户体验查原帖及有关回复。判断可信度时看材料与具体主张的关系：发布者声明、测量、第三方分析、用户自述及 Agent 推断分别使用。沿转载链追原始出处；不同工具或引擎返回同一材料仍归为同一来源。

对比前核对对象与条件，例如不同版本的软件支持范围、不同统计口径的数据，可能解释表面差异。相同条件下仍冲突时保留双方证据，优先补查会改变最终结论的争议。

分别记录发布时间、修订时间、快照／捕获时间及本次取得时间。需要新观察时用 `refresh` 跳过本地 URL 缓存，再核对上游内容的时间与适用状态；本次请求时间只证明此次取得，无法单独证明上游内容已更新。

## 失败与停滞后的行动

| 返回情况 | 处理 |
|---|---|
| 正常空结果／材料无关 | 检查实体、别名、语言和范围，再调整查询或来源；记录本次检索的实际覆盖 |
| 403／访问条件限制 | 保留成功材料，选择当前允许且支持该对象的其他入口 |
| 429／限流 | 遵守 `retryAfterSeconds` 或 `accessFailures[].retryAt`，先处理其他来源或字段；`refresh` 也遵守明确等待条件 |
| 只有标题、页面壳或错误提示 | 结合正文、`metadata.bodyAvailable`、`contentScope` 与 `nextSteps` 判断；按目标材料所需的取得方式接力 |
| 历史正文未取得 | 区分索引、可用报告与实际快照；沿已发现的 URL 与历史域名定位，保留无法取证的时间段 |
| 返回内容截断或只覆盖部分对象 | 按实际游标、页码或范围续读，记录已取得的边界 |
| 部分读取失败／缓存未保存 | 继续使用已返回材料，按 `runs`／`cacheWarnings` 处理缺口 |
| 状态文件保存失败 | 返回的 `state` 和报告继续可用；根据 `stateWarnings` 修复路径或占用后重试 |

每轮先审阅已有材料与未决字段，再选择能增加关键证据的行动。重复查询缺少新信息时，调整方法、补充条件或保留未知。以用户的任务范围与预算为边界，关键结论已得到足够支持时结束；可用路径难以继续补证时，说明已取得结论及剩余缺口。

## 交付核对

对照用户目标逐项说明结论、证据、适用范围与不确定性。比较与推荐同时检查条件符合程度和证据充分性，明确候选与已经充分核验的选项。请求的数量不足时说明覆盖情况与未决原因；页面数、工具调用数和引用数用于描述过程。

结论可以支持或反驳原先说法，也可以暂时未知。检索未命中只说明本次范围内未找到；官方声明、用户反馈和实际观测各按其证据范围交付。关键冲突未解时，将争议与可能改变判断的新证据一并交代。
